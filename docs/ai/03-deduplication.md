# Схема дедупликации

Формат самого токена уже зафиксирован в
[`05-api-contract.md`](./05-api-contract.md) (stateless HMAC, без обращения к
Redis на выдаче) — здесь предмет другой: почему нужен именно **токен как
идентичность**, а не только rate limit по IP, и как из этого выводятся
конкретные пороги.

Разрешение конфликта R13 (анонимность vs дедупликация, см.
`00-task-original.md`) и принцип R14 («ложноположительная блокировка дороже
пропущенной накрутки», `02-load-model.md` §6.8) здесь не переоткрываются, а
применяются к конкретным числам.

---

## 1. Почему rate limit по IP не может быть дедупликацией

Вопрос, с которого начался этот документ: зачем токен, если можно просто
поставить лимит вида «N запросов за T секунд»? Ответ разбивается на два
независимых довода — оба ломают идею, независимо от конкретных N и T.

### 1.1 IP — это не человек

За одним публичным IP одновременно голосуют сотни-тысячи разных людей:
CGNAT крупного мобильного оператора, домашний или офисный Wi-Fi, публичная
сеть. Любой лимит, привязанный к IP, бьёт не по накрутчику, а по всем, кто
физически рядом с ним в топологии сети. Это уже сформулировано как принцип в
`02-load-model.md` §6.8 («если дедупликация по IP отсечёт абонентов за CGNAT
крупного мобильного оператора, потеряются сотни тысяч настоящих голосов и
выборка сместится») — этот документ просто доводит принцип до реализации.

Важно: проблема не в конкретном значении лимита. Хоть 2, хоть 10 — при
разумном IP-лимите на пике телетрансляции он будет задет органическим
трафиком с крупных NAT-узлов раньше, чем распределённой накруткой.

### 1.2 Rate limit ограничивает скорость, а не количество за время жизни опроса

«2 запроса за 60 секунд» — это **скользящее окно**. Окно приёма голосов по
умолчанию 5 минут (`02-load-model.md` §6.4), а не 60 секунд. Через 60 секунд
счётчик обнуляется, и тот же ключ получает ещё 2 попытки — за всё окно
голосования это уже до 10 успешных проходов лимита, а не 2.

Чтобы ограничить именно «не больше одного раза за весь опрос», лимит должен
быть не скользящим окном, а **квотой на время жизни опроса**, привязанной к
стабильному идентификатору. Но это снова требует identity-ключа, а не
конструкции «rate limit по IP» — то есть, даже если зафиксировать окно
квоты равным длительности опроса, ключевая проблема §1.1 (IP ≠ человек)
никуда не девается.

### Вывод

Токен — это не *дополнение* к rate limit, а ответ на другой вопрос: rate
limit ограничивает **скорость запросов с сетевого адреса** (защита от
флуда), токен даёт **анонимную идентичность одного браузера** (собственно
дедупликация). Обе задачи реальны и решаются раздельно — см. §2 и §3.

## 2. Дедупликация: токен как идентичность

### 2.1 Ключ

```
d:{poll_id}:{nonce}
```

`nonce` — случайная часть самоподписанного токена (`05-api-contract.md`), не
весь токен целиком: полный токен включает подпись и `expires_at`, что делает
ключ длиннее без пользы для уникальности. `nonce` — 128 бит, что даёт то же
обоснование памяти, что и в `02-load-model.md` §4.4 (~100 байт на голос с
учётом накладных расходов Redis).

### 2.2 Операция

Проверка и инкремент — один атомарный Lua-вызов, уже описанный в
`01-stack.md`:

```lua
if redis.call('SET', dedup_key, 1, 'NX', 'EX', ttl) then
    redis.call('HINCRBY', counter_key, option_id, 1)
    return 1
end
return 0
```

Ровно один голос на токен. Не «мягкий» лимит с несколькими попытками —
`SET NX` бинарен по конструкции, и это осознанно: смягчать до «K попыток на
токен» означало бы просто поднять цену накрутки в K раз ценой равного
усложнения кода, не решая проблему принципиально.

### 2.3 TTL — привязан к закрытию опроса, не к фиксированной длительности

`expires_at` токена (поле в `VoteToken`, `api/openapi.yaml`) и TTL
dedup-ключа в Redis — оба равны **моменту закрытия опроса** (`closes_at`) с
запасом, а не фиксированному «N минут от выдачи». Если зафиксировать TTL
токена как константу от момента выдачи, получаем два симметричных бага:

- токен, выданный за минуту до `closes_at`, живёт дольше окна голосования —
  им можно проголосовать уже после закрытия, если константа больше остатка
  окна;
- токен, выданный сразу после открытия голосования, может протухнуть раньше
  `closes_at`, если константа меньше полной длины окна, — реальный зритель
  получит немотивированный `401` на валидную попытку.

Поэтому:

```
token.expires_at = poll.closes_at
dedup_key TTL     = seconds_until(poll.closes_at) + grace   (grace = 60s)
```

`grace` — запас на in-flight запросы и рассинхрон часов между инстансами,
тот же принцип «плюс запас», что уже сформулирован в `01-stack.md` для TTL
дедуп-ключей в целом.

### 2.4 Почему это не нарушает анонимность (R13)

Токен — чистая случайность, подписанная сервером, без какой-либо привязки к
личности голосующего (IP в подпись не входит, cookie не содержит PII).
Единственный факт, который сервер способен восстановить по dedup-ключу, —
«этим токеном уже голосовали»; какой вариант был выбран, из ключа `d:*` не
восстановить (это делает `HINCRBY` на агрегированный `counter_key`, отдельно
и без связи с конкретным токеном в хранилище). После истечения TTL ключ
исчезает сам — Redis ничего не хранит дольше времени жизни опроса плюс
запас.

## 3. Rate limit: не дедупликация, а защита от флуда

Роль, которая изначально предлагалась для «2 запроса за 60 секунд», у
rate-лимитера остаётся — но с другой формулировкой цели: не «не более N
голосов с адреса», а «не быстрее X запросов в секунду с адреса», не
привязываясь к результату (успешный голос это был или дубликат).

### 3.1 Что лимитируется

Лимит общий для `POST /v1/polls/{id}/token` и `POST /v1/polls/{id}/votes`,
ключ — IP, реализация — скользящее окно на Lua в Redis (решение уже
зафиксировано в `01-stack.md`, раздел «Что сознательно не берём»: свой
rate-limiter на Go не годится, потому что лимит должен быть общим для всех
инстансов).

Зачем лимитировать ещё и `/token`, если дедуп всё равно на уровне
голосования: без этого скрипт с одной машины может в цикле «получить
токен → проголосовать» обходить дедуп бесконечно — каждый токен свежий и
формально не дубликат. Лимит на `/token` — это первый, более дешёвый
барьер (отсекает до траты Redis-записи на голосование), лимит на `/votes` —
второй, окончательный. Это ровно тот класс атаки («один скрипт с одного
IP»), который R2 требует останавливать; распределённый пул прокси —
явно нет (`00-task-original.md`, «сознательно не входит в скоуп»).

### 3.2 Порог

| Параметр | Значение | Статус |
|---|---|---|
| Лимит | 60 запросов / 10 секунд на IP, суммарно по `/token` + `/votes` | **черновой, требует проверки замером** |
| Реализация | скользящее окно, Lua, тот же Redis-кластер | зафиксировано |

Число намеренно щедрое, а не «наилучшая оценка реального флуда» — по той же
причине, что и в §1.1: у нас нет данных о том, сколько органического трафика
может дать один узел CGNAT крупного оператора в пиковые 30 секунд эфира, а
цена ошибки в меньшую сторону (реальные зрители получают 429) выше цены
ошибки в большую (лимит ловит только совсем явный флуд с одной машины —
на порядок выше правдоподобной органической частоты). Это тот же принцип,
что уже применён к порогам деградации в `02-load-model.md` §6.7. Пороговое
значение — кандидат на пересмотр по k6-замеру, как и остальные допущения
из таблицы в `02-load-model.md` §8.

### 3.3 Ответ клиенту

`429` с `Retry-After` и случайным разбросом — уже описано в
`05-api-contract.md` и `02-load-model.md` §6.7 (уровень 1 деградации).
Отдельного механизма для этого документа не требуется, лимит `/token`
переиспользует тот же ответ.

## 4. Обход дедупликации — и почему это приемлемо

Токен живёт в cookie и localStorage. Достаточно очистить оба хранилища или
открыть приватное окно — и дедуп обнуляется для этого человека. Это не
недостаток реализации, а прямое следствие требования R2 («не слишком
защищённая от обхода, достаточная на уровне обычных, не технически
подкованных пользователей», `00-task-original.md`). Считать это уязвимостью
и закрывать её (device fingerprinting, привязка к номеру телефона,
CAPTCHA) значило бы нарушить R2 явно — эти варианты уже отклонены в
`01-stack.md` («Что сознательно не берём») по этой же причине.

Порог осознанно занижен в сторону «пропустить накрутку», а не «заблокировать
лишнего» — прямое следствие R14.

### 4.1 Почему ручной обход не масштабируется

Мало сказать «это допустимо по R2» — стоит явно проговорить, почему это ещё
и безопасно с точки зрения чисел, а не просто разрешённая дыра.

Один человек, вручную открывающий приватные окна или чистящий данные сайта,
физически ограничен скоростью собственных рук — это единицы, в пределе
десятки повторных голосов на человека, не тысячи. На фоне базового сценария
в 5М голосов (`02-load-model.md`) это статистически неотличимо от шума —
тот же аргумент чувствительности, что уже применён к порогам деградации в
§6.7 того документа.

Единственный способ превратить это в реальную угрозу результатам —
**автоматизация**: скрипт, гоняющий `POST /token` → `POST /votes` в цикле,
может повторять то же самое действие тысячи раз в секунду с одной машины.
Но это уже другая проблема, и её решает не токен, а IP rate limit из §3 —
запросы на выдачу токена и на голосование ограничены по скорости
независимо от того, свежий токен в каждом запросе или нет. Итого: токен
закрывает *массовый* и *случайный* кейс (обычный зритель, обновивший
страницу), rate limit — *массовый* и *автоматизированный* (скрипт с одной
машины); *единичный осознанный* обход одним человеком остаётся открытым
намеренно, как и требует R2, и не масштабируется в проблему без
автоматизации, которая уже закрыта отдельным механизмом.

## 5. Что сознательно не делаем

| Что | Почему нет |
|---|---|
| Жёсткий лимит голосов на IP | §1.1 — блокирует реальных пользователей за CGNAT/общим Wi-Fi. |
| Device fingerprinting | Утяжеляет фронтенд, спорно с точки зрения приватности, не нужен против threat model R2. |
| CAPTCHA / proof-of-work на `/token` | Прямо исключено `01-stack.md` — вредит конверсии на массовой ТВ-аудитории, задание явно просит «не слишком защищённую» схему. |
| Защита от пула прокси | Явно вне скоупа, `00-task-original.md`. |
| Наблюдение «доля дублей по IP» как продуктовый сигнал | Полезная идея (упомянута в `01-stack.md` про `votes_rejected_total{reason="duplicate"}`), но это агрегированная метрика по всей системе, а не по IP — разбивка по IP добавляет новую сущность в хранилище и логирование ради наблюдаемости, которую сейчас никто не просил; можно добавить позже без изменения контракта. |

Этот документ фиксирует **ключ, TTL и оператора** дедупликации — это
единственное, что было нужно для завершения `05-api-contract.md`. Число
