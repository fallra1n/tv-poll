# Фронтенд

Frontend добавлен после фиксации backend-архитектуры и wire-контракта. Его
единственный источник истины о JSON, статусах и endpoint'ах —
[`api/openapi.yaml`](../../api/openapi.yaml). Текущее состояние параллельно
разрабатываемого backend-кода намеренно не использовалось как контракт.

## Основа: PBS, но не копия приложения

Из локального PBS-шаблона взяты Bun, React 19, Tailwind CSS 4,
shadcn/Base UI, строгий TypeScript и принцип «прямой код раньше абстракции».
Не перенесены FastAPI, Python/uv, demo-экран, логотип и раздача `dist` через
backend: по `02-load-model.md` статика должна находиться на CDN.

PBS распространяется по MIT; текст лицензии сохранён в
`frontend/THIRD_PARTY_NOTICES.md`.

## Два entrypoint

Публичное голосование и админка собираются отдельно:

| Entry | URL | Содержимое |
|---|---|---|
| public | `/polls/{pollId}` | определение опроса, токен, один POST голоса |
| admin | `/admin/*` | Bearer auth, формы, FSM, polling, Recharts |

Причина — 7–28 млн потенциальных загрузок публичной страницы по модели из
`02-load-model.md`. Recharts, router и admin-формы не должны попадать в её
entry chunk. Bun выносит только действительно общие React/UI-зависимости.

## Публичный flow

1. UUID берётся из `/polls/{pollId}` и проверяется до сетевого запроса.
2. `GET /v1/polls/{id}` отправляется без credentials, чтобы не мешать CDN.
3. Фаза `scheduled/open/closed` вычисляется по `opens_at`/`closes_at`; поля
   `state` в публичном ответе нет намеренно.
4. `POST /token` выполняется один раз. Одновременные вызовы объединяются в
   один Promise, в том числе при двойном effect в React StrictMode.
5. Токен хранится по poll ID в `localStorage`, но остаётся в памяти при
   блокировке storage. Cookie и `X-Vote-Token` отправляются параллельно.
6. После `201` локально сохраняется только общий статус `accepted`, не
   выбранный вариант. `409 duplicate` считается терминальным «уже учтён».
7. `409 closed` внутри расчётного окна не объявляется окончательным
   закрытием: фактический переход scheduled → open может задержаться, поэтому
   пользователь может повторить запрос.
8. `429` учитывает серверный `Retry-After`; бесконечного auto-retry нет.

## Админка

Статический `ADMIN_TOKEN` нельзя помещать в `BUN_PUBLIC_*`: это встроило бы
секрет в JS. Пользователь вводит токен вручную, он хранится в
`sessionStorage` и удаляется при `401` или выходе.

Реализованы список с фильтром/pagination, создание draft или scheduled
опроса, разрешённые переходы FSM, обезличенные результаты и timeseries.
Во время open результаты обновляются раз в секунду без наложения запросов;
polling приостанавливается в скрытой вкладке. Время `snapshot_at` и факт
sampling показываются явно.

## Уточнение контракта

При реализации обнаружилось внутреннее противоречие OpenAPI: `PollAdmin`
наследовал обязательные string-поля `opens_at`/`closes_at` от `PollPublic`,
но `POST /admin/polls` может вернуть draft без расписания. Согласованное
решение: общие поля вынесены в `PollDefinition`; у `PollPublic` даты
обязательны и non-null, у `PollAdmin` обязательны, но nullable до
планирования.

## Что сознательно не берём

| Решение | Почему нет |
|---|---|
| Одна SPA | повышает риск загрузить admin-only код миллионам зрителей |
| SSR/Next.js | страница статична, а отдельный runtime усложняет CDN-границу |
| Admin token в env frontend | любой публичный build раскрывает секрет |
| WebSocket | контракт и `01-stack.md` фиксируют polling раз в секунду |
| Публичные результаты | endpoint отсутствует намеренно |
| Redux/Zustand | состояние локально каждому короткому flow |
| Runtime schema library | OpenAPI-типы и небольшое число явных type guard достаточны |

## Проверка

- OpenAPI: Redocly, валидная спецификация с четырьмя ранее существовавшими
  предупреждениями.
- Unit/API/компонентные: 18 тестов на даты, маршруты, headers, ошибки, token
  storage и автомат состояний `poll-page.tsx` (accepted/duplicate/closed/
  rate-limited) через `@testing-library/react`.
- E2E: public vote и создание draft в desktop/mobile Chromium — на моках
  (`e2e/app.spec.ts`), плюс отдельный `e2e/live-backend.spec.ts` против
  настоящего `make up` (пропускает себя, если бэкенд не поднят), проверяющий
  то, что мок не может: реальные CORS-заголовки, реальный cookie/token обмен
  и что повтор токена бэкенд действительно отклоняет как дубликат.
- Oxlint, TypeScript и production build проходят.
- Ручной прогон полного цикла (создание → расписание → авто-открытие →
  голос → результаты вживую → закрытие) против `make up` — покрывает то, что
  ни один из тестов выше не проверяет: реальные сетевые задержки и
  eventually-consistent снапшот сразу после закрытия.

### Интеграция с живым бэкендом — что нашлось только на этом шаге

Фронтенд был написан и провалидирован только против `api/openapi.yaml`, пока
бэкенд разрабатывался параллельно (`sessions/01-frontend.md`). Когда бэкенд
стал готов и это ограничение снялось, первый прогон против настоящего
`make up` нашёл два расхождения, ни одно из которых не видно ни в спеке, ни
в моках — только в браузере против реального сервера:

- `corsMiddleware` не выставлял `Access-Control-Expose-Headers`, поэтому
  `Retry-After` на 429 был непрочитан из JS (весь rate-limit UX работал на
  угадываемой задержке). Исправлено в бэкенде.
- `429` на `/votes` отдавал конверт `Error`, а не `VoteRejected`, как того
  требует `api/openapi.yaml` — расхождение реализации со своим же
  контрактом, обнаруженное только диффом, не тестом. Исправлено в бэкенде.

Также за это время контракт успел уйти на две ревизии вперёд генерации типов
фронтенда (`VoteRejected.option_id`, `PollResults.snapshot_at` — nullable) —
типы перегенерированы, оба поля используются (см. `what-ai-got-wrong.md`).
