# Стек технологий (backend)

Документ покрывает **только серверную часть**. Фронтенд разрабатывается
отдельно и общается с сервисом по HTTP JSON API — следствия этого разделения
описаны в разделе «Граница с фронтендом».

Числовые обоснования, на которые ссылается этот документ, — в
[`02-load-model.md`](./02-load-model.md).

---

## Принцип отбора

Задание проверяет не знание модных библиотек, а способность выбрать
минимальный набор компонентов под конкретный профиль нагрузки. Профиль здесь
необычный: **write-heavy, короткий предсказуемый пик, агрегированное чтение**.

Поэтому каждый пункт ниже проходил три вопроса:

1. Решает ли он проблему, которая реально возникает при 100k RPS на пике?
2. Можно ли обойтись стандартной библиотекой или уже выбранным компонентом?
3. Сможет ли ревьюер поднять это одной командой и понять за 5 минут?

Компонент, не прошедший все три, уезжает в раздел «Что сознательно не берём».

## Обоснования по пунктам

### Go

Задан условиями (тестовое на бэкенд, мой основной язык), но для этой задачи
он и по существу удачен: goroutine-per-request дёшев при десятках тысяч
одновременных соединений, GC-паузы при таком профиле аллокаций (маленькие
короткоживущие объекты) укладываются в субмиллисекунду, а один бинарник без
рантайма упрощает прескейлинг перед эфиром.

Ограничение, о котором стоит помнить: на 100k RPS заметная доля CPU уходит не
на бизнес-логику, а на TLS-хендшейки и парсинг HTTP. Это лечится терминацией
TLS на балансировщике и keep-alive, а не оптимизацией Go-кода.

### `net/http` + chi

С Go 1.22 в стандартном роутере появились method-паттерны и path-параметры
(`POST /polls/{id}/vote`), поэтому базовый роутинг закрывается stdlib. chi
берётся ради `middleware`-цепочки (request ID, recovery, timeout, CORS) и
группировки роутов — писать это руками ради экономии одной зависимости смысла
нет.

**Почему не Fiber/Echo/Gin.** Fiber построен на fasthttp и несовместим с
`net/http`-интерфейсами: теряются стандартные middleware, `httptest`,
`context`-семантика. Выигрыш в бенчмарках достигается на синтетических
хендлерах без I/O; у нас каждый запрос упирается в round-trip до Redis, и
разница в аллокациях роутера теряется в шуме. Gin — это тот же `net/http` с
своим контекстом; в 2026 году его основное преимущество (роутинг) закрыто
стандартной библиотекой.

### Redis как горячий путь

> **Пересмотрено при реализации** (см. `docs/ai/sessions/02-backend.md`).
> Всё в этом разделе ниже — Lua-скрипт, инкремент счётчика в Redis на каждый
> голос, искусственное шардирование `counts:{0..N}` — было заменено при
> кодировании. Причина не «стало лучше на вкус», а две конкретные находки:
> во-первых, скрипт с 4 ключами (`meta`, dedup, `counts:{shard}`,
> `rejected:{shard}`) физически не выполняется в Redis Cluster —
> `CROSSSLOT Keys in request don't hash to the same slot`, воспроизведено на
> реальном Redis 7 до того, как это было закодировано; во-вторых, сам довод
> «Lua даёт атомарность без транзакций» оказался неверным — `SET NX`
> атомарен сам по себе (500 параллельных `SET k 1 NX` на реальном Redis дают
> ровно один `OK`), Lua для этого не нужен. Текст ниже оставлен, потому что
> показывает, почему первое решение выглядело обоснованным, а не только то,
> чем его заменили.

Ключевое архитектурное решение осталось верным: **на горячем пути
голосования нет обращений к PostgreSQL**. Но приём голоса — это не
Lua-скрипт, а **одна команда Redis**:

```
SET d:{poll_id}:{nonce} {option_id} NX GET EX ttl
```

- Если ключа не было — `NX` даёт `SET` пройти, ответ `GET` — `nil`: голос
  принят.
- Если ключ уже есть — `SET` не выполняется (значение не перезаписывается),
  `GET` возвращает то, что записал первый, успешный голос: явный дубликат,
  и клиенту можно сообщить, каким вариантом он уже проголосовал (полезно,
  если первый ответ потерялся в сети и клиент ретраит тем же токеном).

Почему этого достаточно без Lua и без транзакции:

- **Атомарность даёт сама команда.** `SET ... NX` — одна операция на стороне
  Redis, гонки между «проверить» и «записать» нет по построению: два
  конкурентных запроса с одним ключом всегда упорядочиваются сервером, и
  ровно один получает успешную запись. Verified — 200 конкурентных вызовов
  одним nonce в интеграционном тесте (`internal/store/redisstore`) дают
  ровно один `accepted`.
- **Счётчик — не в Redis на пути голоса.** Принятый голос инкрементит
  atomic-счётчик в памяти самого Go-инстанса (`internal/counter`); в Redis
  эти дельты уезжают раз в секунду одним `HINCRBY`-пайплайном на все опции
  сразу, а не по одному инкременту на голос. Отсюда и решение про hot key
  ниже: писать в Redis 15–20 раз в секунду на опрос — не проблема, которую
  нужно шардировать, в отличие от 75 000 раз в секунду.
- **Естественный TTL.** Ключи дедупа живут ровно столько, сколько идёт опрос
  плюс запас (`docs/ai/03-deduplication.md` §2.3). Их не надо чистить
  джобой — Redis удалит сам.

**Hot key: проблема, которую больше не нужно решать.** Опрос в момент эфира
ровно один живой, поэтому наивный вариант «инкремент счётчика в Redis на
каждый голос» действительно упёрся бы в единственный ключ/шард при 75k RPS —
и именно это изначально оправдывало искусственное шардирование
`counts:{0..N-1}`. Раз счётчик больше не пишется в Redis на каждый голос (см.
выше), это узкое место просто не возникает: `poll:{id}:counts` — один ключ,
но частота записи в него ограничена не темпом голосования, а темпом флаша
(раз в секунду), так что шардировать нечего. Единственное, что действительно
пишется в Redis на каждый голос, — dedup-ключ `d:{poll_id}:{nonce}`, и он
шардируется сам собой, потому что `nonce` случаен.

**Что при падении Redis.** Данные в нём — не источник истины дольше секунды:
воркер периодически снимает снапшот счётчиков в Postgres. При падении теряется
максимум окно между снапшотами. Для опроса это приемлемо и должно быть
проговорено; альтернатива (синхронная запись каждого голоса в durable-хранилище)
не выдержит целевого RPS.

**Почему не memcached.** Нет `GET` вместе с `SET NX` в одной команде —
пришлось бы делать две операции с гонкой между ними, теряя ровно то
свойство, ради которого выбран `SET ... NX GET`.

### PostgreSQL как холодное хранилище

Postgres хранит то, что должно пережить перезапуск и требует реляционной
целостности: опросы, варианты ответов, окна голосования, состояния
(`draft → scheduled → open → closed`), снапшоты результатов с таймстемпом,
аудит действий администратора.

Нагрузка на него измеряется единицами запросов в секунду: админка — это
десяток человек, снапшоты — один воркер раз в секунду. Никакого тюнинга и
шардирования не требуется, и это стоит явно сказать в README, чтобы не
выглядело, будто вопрос упущен.

Снапшоты дают побочную пользу: из них строится **динамика голосования по
времени**, а это ровно та картинка, которую хочет видеть опросная компания в
админке.

**Почему не ClickHouse.** Он был бы уместен, если бы мы писали каждый голос
как событие для последующей аналитики по срезам. Мы этого не делаем сознательно
(см. R8 + анонимность), поэтому колоночная СУБД решала бы несуществующую задачу.

### pgx без ORM

`pgx` — нативный протокол PostgreSQL, без прослойки `database/sql`, с
поддержкой пула и batch-запросов. Запросы пишутся руками.

**Почему не GORM.** Схема здесь маленькая (4–5 таблиц), запросов немного, и
все они простые. ORM дал бы экономию на CRUD админки и отнял бы контроль над
тем, что уходит в базу, — плохой размен, когда обсуждение производительности
является частью сдачи. `sqlc` рассматривался как компромисс (типобезопасность
из SQL), но добавляет шаг кодогенерации в сборку ради небольшого выигрыша.

### `log/slog` вместо zap/zerolog

Структурные логи нужны, но профиль логирования тут специфический: **на горячем
пути логировать каждый голос нельзя**. 100k строк в секунду — это отдельная
проблема с доставкой и хранением, которая больше самой задачи. Логируются
только ошибки и агрегированные события, объём маленький, разница в
производительности между slog и zap нерелевантна. Stdlib выигрывает по числу
зависимостей.

### Prometheus-метрики

Это не украшательство, а прямое доказательство, что расчёты из
`02-load-model.md` проверялись, а не выдумывались. Минимальный набор:

- `votes_accepted_total`, `votes_rejected_total{reason}` — reason различает
  дубликат, закрытый опрос, rate limit;
- гистограмма латентности хендлера голосования (нужен p99, не среднее);
- `redis_command_duration_seconds` — чтобы видеть, когда упирается Redis;
- `inflight_requests` — для наблюдения за насыщением.

`votes_rejected_total{reason="duplicate"}` дополнительно полезна продуктово:
резкий рост доли дубликатов во время эфира — сигнал о накрутке.

### Аутентификация админки

Bearer-токен из переменной окружения, сравнение через
`subtle.ConstantTimeCompare`. Полноценные пользователи, роли и refresh-токены
для тестового — лишний объём, который отвлекает от сути. В README фиксируется,
что в проде это заменяется на OIDC/SSO компании.

Важно, что публичные эндпоинты голосования и админские разведены по разным
роутерам с разными middleware: у первых нет авторизации, но есть rate limit, у
вторых наоборот.

### Тесты

- **Юнит-тесты** на чистую логику: валидация опроса, FSM переходов, подпись и
  разбор токена (включая ротацию секрета и все варианты битой wire-строки),
  локальный rate limiter, swap/restore семантика in-memory счётчиков,
  merge-функция монотонности снапшотов (чистая, без БД — см.
  `docs/ai/04-data-model.md`).
- **Интеграционные** через `testcontainers-go`: поднимают реальные Redis и
  Postgres по отдельности, проверяют атомарность `SET NX GET` (гонки в ней
  юнит-тестом не поймать), идемпотентность голосования, корректность
  снапшотов и лидерства.
- **Конкурентный тест** отдельно: N горутин отправляют одну и ту же claim-
  операцию (`SET NX GET`) с одним nonce, утверждается ровно один принятый
  голос. Это тест, который прямо подтверждает корректность дедупа —
  `internal/store/redisstore`, 200 горутин, реальный Redis 7.

`testcontainers` предпочтён моку Redis (`miniredis`), потому что miniredis
эмулирует нужную здесь комбинацию флагов (`SET ... NX GET EX` разом) неполно
— единственная команда на горячем пути обязана быть проверена буквально на
том движке, который будет её исполнять в проде, а не на его приближении.

### k6 для нагрузочного тестирования

Сценарий с `ramping-arrival-rate`, воспроизводящий форму кривой из
`02-load-model.md`: резкий рост, пик, длинный хвост. Результаты замера
попадают в README таблицей. Сам сценарий лежит в репозитории, чтобы ревьюер мог
воспроизвести.

Выбран вместо `vegeta` и `wrk` из-за поддержки сценариев с состоянием: перед
голосованием нужно получить токен, то есть это двухшаговый флоу, а не
плоский обстрел одного URL.

### OpenAPI рукописный

Спека пишется руками и используется как контракт с фронтендом. Кодогенерация
(`oapi-codegen`) не берётся: хендлеров мало, а сгенерированный код хуже
читается ревьюером, который смотрит репозиторий 20 минут.

## Граница с фронтендом

Раз фронтенд отдельный, есть три следствия, которые надо решить на стороне
бэкенда:

**1. CORS.** Список разрешённых origin — из конфигурации, не `*`, потому что
запросы идут с credentials.

**2. Где живёт токен голосования.** Проблема: фронтенд на другом origin, а
значит cookie требует `SameSite=None; Secure` и `credentials: 'include'` —
работает, но ломается в браузерах с блокировкой сторонних cookie, которых у
массовой аудитории с ТВ будет много. Решение — **два уровня**: сервер и ставит
cookie, и возвращает токен в теле ответа. Фронтенд кладёт его в `localStorage`
и шлёт заголовком `X-Vote-Token`. Сервер принимает любой из источников.
Для «обычного, технически не подкованного пользователя» (R2) это ровно нужный
уровень: очистка одного хранилища не помогает, нужно чистить оба или идти в
инкогнито.

**3. Контракт на выдачу опроса.** Определение активного опроса иммутабельно и
отдаётся с агрессивным `Cache-Control` — чтобы фронтенд мог положить его на CDN
и не бить в бэкенд 100М раз. В бэкенд летит только маленький POST с голосом.
Это принципиально: без CDN на статике сервис ляжет на раздаче, а не на приёме
голосов.

## Что сознательно не берём

| Технология | Почему нет |
|---|---|
| Kafka / NATS JetStream | Буфер между API и агрегацией выглядит логично, но Redis уже играет эту роль. Брокер добавил бы компонент в compose, гарантии доставки, консьюмер-группы и лаг-мониторинг — ради проблемы, которой при выбранной схеме нет. Описан в README как следующий шаг, если понадобится durable-лог каждого голоса. |
| Kubernetes / Helm | Задание требует локального запуска. Стратегия прескейлинга описывается текстом. |
| gRPC | Клиент — браузер массового пользователя. HTTP/JSON безальтернативен. |
| ClickHouse | Отдельные голоса не сохраняются принципиально. |
| ScyllaDB / Cassandra | Решают проблему durable-записи на большом RPS, которая снята отказом от хранения индивидуальных голосов. |
| WebSocket для live-результатов | 100М открытых соединений — отдельная инженерная задача. Админке (десяток человек) хватит polling раз в секунду. |
| Captcha / Play Integrity | Прямо противоречит R2 («не слишком защищённая») и вредит конверсии на массовой ТВ-аудитории. Упоминается в разделе про границы дедупликации. |
| Lua-скрипт голосования | Изначальный выбор этого документа, пересмотрен при реализации — см. врезку в начале раздела «Redis как горячий путь» выше и `docs/ai/sessions/02-backend.md`. Корректность даёт атомарность самой команды `SET NX`, скрипт не добавляет гарантий, которых не было бы без него, а 4-ключевая версия скрипта физически не работает в Redis Cluster (`CROSSSLOT`). |
| Redis-based rate limiter на скользящем окне (Lua) | Тоже пересмотрено при реализации: `docs/ai/03-deduplication.md` §3.2 обосновывает щедрый, непроверенный порог (60/10с) именно как защиту от одного скрипта с одной машины, а не от распределённой атаки — а если цель именно эта, локальный token bucket на процесс закрывает её при нуле дополнительных обращений к Redis на голос. Вывод ниже это не отменяет: лимит НЕ шардируется по инстансам специально не потому, что это невозможно, а потому что при таком пороге (в разы выше органического трафика) недостаточная согласованность между инстансами не имеет значения для заявленной угрозы. |

## Открытые вопросы к следующим документам

- Точная схема дедупликации и подбор порогов — отдельный документ.
- Формат токена (HMAC-подпись против случайного opaque-значения в Redis).
- Период снапшотов — выводится из замеров k6. Число шардов счётчиков снято
  с повестки при реализации: счётчики больше не пишутся в Redis на каждый
  голос (см. «Redis как горячий путь» выше), шардировать нечего.
