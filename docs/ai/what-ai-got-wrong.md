# Что ИИ сделал неправильно

Этот файл фиксирует найденные ошибки, а не только итоговое решение.

## Лишняя проверка backend history

При исследовании frontend-задачи была предложена команда `git show` для
backend-коммита. Это смешивало закреплённый wire-контракт с незавершённой
реализацией. Пользователь уточнил границу: frontend зависит от
`api/openapi.yaml`, а не от текущего backend worktree.

## Предположение о Bun browser env

Наличие `env = "BUN_PUBLIC_*"` в `bunfig.toml` не означает, что ссылка на
неопределённую переменную `process.env` безопасна в браузере. Playwright
обнаружил runtime crash. Исправление — browser-safe fallback плюс установка
default перед production build.

## Слишком общий HMR helper

Вынос `import.meta.hot.data` в helper выглядел как устранение дублирования,
но нарушил ограничение Bun: HMR data должна читаться непосредственно в
entrypoint. Две небольшие явные реализации оказались правильнее абстракции.

## Непроверенный deep-link routing

Admin shell собирался, но Routes не совпадали с `/admin/*`. TypeScript и
production build этого не выявили; ошибка нашлась только в browser e2e.
Вывод: для статических SPA fallback недостаточно проверить bundle — нужен
реальный переход напрямую на глубокий URL.

## Относительные assets

Первый build был технически успешен, но сгенерировал относительные ссылки.
При CDN fallback они ломались бы на динамическом URL опроса. Проверка
содержимого `dist/*.html` обязательна наряду с успешным exit code сборки.

## Backend

Подробный ход реализации — `sessions/02-backend.md`. Здесь только сами
ошибки, без контекста находки.

### Lua-скрипт голосования не работает в Redis Cluster

Спроектирован в `04-data-model.md` с 4 ключами на скрипт (`meta`, dedup,
`counts:{shard}`, `rejected:{shard}`), рандомизированными независимо друг от
друга. На реальном Redis 7 в cluster-режиме — `CROSSSLOT Keys in request
don't hash to the same slot`. Заявленное обоснование Lua («атомарность без
транзакций») тоже оказалось неверным: `SET NX` атомарен сам по себе, 500
параллельных вызовов на реальном Redis дают ровно один `OK`. Найдено и
исправлено до того, как это стало кодом — не постфактум.

### Кеш определений не различал `draft`

Fetch-through кешировал результат независимо от `state`. Опрос, однажды
запрошенный в `draft` (404), навсегда оставался закешированным как 404 даже
после публикации. Пойман конкретной последовательностью: создать → `GET` →
запланировать → `GET` снова. Исправление — `draft` не кешируется вообще.

### Кеш давал ложный отказ сразу после открытия голосования

После фикса выше нашлась противоположная гонка: голос в первую секунду после
`scheduled → open` видел устаревшее `scheduled` в кеше и получал `409 closed`
— ложный отказ реального голоса, худшая сторона ошибки для опросной компании
(R14). Исправление — синхронная запись в кеш сразу при переходе состояния
(`cache.Cache.Put`), не ожидание секундного фонового тика.

### Rate limiter делил бюджет между опросами

Ключ лимитера был привязан только к IP, а должен — к `(poll_id, IP)`: один
IP на двух разных опросах делил бы один бюджет. Найдено при проектировании,
до того как стало проблемой в реализации голосования.

### FK-конфликт ронял audit log в `/internal/warmup`

`admin_audit_log.poll_id` — настоящий foreign key. Несуществующий `poll_id`
из тела запроса, переданный напрямую в FK, ронял `INSERT` и терял запись
аудита ровно в том случае («оператор ошибся в ID»), где она важнее всего,
хотя HTTP-ответ оставался `202`. Исправление — в FK только существующий
`poll_id`, факт попытки и `poll_found: false` — в `detail` без ограничения.
