# Модель данных: Postgres, Redis, и зазор между ними

Это последний документ из изначально запланированной тройки 03/04/05
(`README.md`). К этому моменту токен и dedup-ключ уже зафиксированы
(`03-deduplication.md`), а wire-контракт — в `api/openapi.yaml`. Здесь —
собственно таблицы и Redis-ключи, из которых всё это собирается.

## Найденная по пути ошибка, которую стоит зафиксировать явно

Пока раскладывал таблицы, обнаружился реальный конфликт с уже принятыми
решениями, а не гипотетический. `02-load-model.md` §4.2 описывает хендлер
голосования так: «разбор JSON → проверка HMAC-подписи токена → один
`EVALSHA` в Redis → сериализация ответа. **Никаких обращений к Postgres**».
Но нигде не сказано, откуда хендлер на этом пути берёт три вещи, без
которых он не может ни принять, ни отклонить голос:

- `state` опроса (открыт ли приём),
- `closes_at` (не истекло ли окно),
- множество валидных `option_id` (чтобы отклонить мусорный `option_id`
  с `400`, а не молча инкрементить несуществующий вариант).

Если это читать из Postgres на каждый голос — прямое нарушение «никаких
обращений к Postgres» и лишний round-trip сверх заявленного. Если каждый
Go-инстанс кеширует это в памяти процесса — возникает риск рассинхрона
между инстансами (один узнал о ручном закрытии опроса раньше другого, и
кто-то продолжает принимать голоса после закрытия — уже не «безобидная»
неточность, а нарушение целостности результата).

Решение — в §2.3 ниже: эти поля живут в самом Redis, и Lua-скрипт читает их
**в рамках того же `EVALSHA`**, а не отдельным вызовом. Round-trip
по-прежнему один (клиент делает один сетевой вызов к Redis), просто внутри
этого одного вызова Lua теперь выполняет не две Redis-команды, а четыре-пять
— это не сетевые операции, они не стоят лишних round-trip'ов, и заявленный
в `02-load-model.md` бюджет латентности не нарушается.

> **Как это разрешилось при реализации.** Забегая вперёд относительно §2:
> Lua-путь выше не пережил кодирование по независимой причине (CROSSSLOT,
> см. §2). В итоге выбор всё же пал именно на вариант, который этот раздел
> называл рискованным, — кеш в памяти каждого Go-инстанса, а не
> Redis-зеркало. Названный здесь риск («один инстанс узнал о переходе
> раньше другого») оказался не гипотетическим: именно он и произошёл при
> тестировании (голос сразу после `open` видел устаревшее `scheduled`),
> только не между «ручным закрытием» и приёмом голосов, как предполагалось
> здесь, а между `scheduled → open` и приёмом. Решение — не Redis-зеркало,
> а синхронная запись в кеш инстанса, обработавшего переход, плюс
> секундный фоновый опрос для остальных — см. §3.

## 1. PostgreSQL

Четыре таблицы — ровно то, что перечислено в `01-stack.md` («опросы,
варианты ответов, окна голосования, состояния, снапшоты результатов,
аудит действий администратора»), ничего сверх.

### 1.1 `polls`

> **Обновлено при реализации.** `opens_at` как отдельная колонка убрана.
> Причина — не связана с триггером ниже (та история осталась в силе как
> есть): при пересмотре `GET /v1/polls/{id}` выяснилось, что если публичный
> ответ должен быть неизменяемым и кешируемым уже с момента `scheduled` (не
> только `open` — см. `05-api-contract.md`), то у него должен быть один
> вход, известный на момент планирования, а не два поля, одно из которых
> (`opens_at`) заполняется только при фактическом открытии. `scheduled_at`
> стал этим единственным входом для `closes_at`; добавлено `opened_at` —
> момент, когда опрос **фактически** перешёл в `open` (может отличаться от
> `scheduled_at` на секунды из-за прескейлинга) — как чисто информационное
> поле, не влияющее на `closes_at`.

```sql
CREATE TABLE polls (
    id                     UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    question               TEXT NOT NULL CHECK (length(question) BETWEEN 1 AND 500),
    state                  TEXT NOT NULL DEFAULT 'draft'
                               CHECK (state IN ('draft', 'scheduled', 'open', 'closed')),

    scheduled_at           TIMESTAMPTZ,
    voting_window_seconds  INTEGER NOT NULL DEFAULT 300 CHECK (voting_window_seconds >= 30),
    closes_at              TIMESTAMPTZ,
    opened_at              TIMESTAMPTZ,
    closed_at              TIMESTAMPTZ,

    created_at             TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at             TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE OR REPLACE FUNCTION polls_set_closes_at() RETURNS TRIGGER AS $$
BEGIN
    IF NEW.scheduled_at IS NOT NULL THEN
        NEW.closes_at := NEW.scheduled_at + NEW.voting_window_seconds * INTERVAL '1 second';
    ELSE
        NEW.closes_at := NULL;
    END IF;
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER polls_closes_at_trigger
    BEFORE INSERT OR UPDATE OF scheduled_at, voting_window_seconds ON polls
    FOR EACH ROW EXECUTE FUNCTION polls_set_closes_at();

CREATE INDEX polls_state_idx ON polls (state);
```

Решения, которые стоит объяснить:

- **`closes_at` считает триггер, а не приложение — и не `GENERATED ALWAYS
  AS`.** Первая версия этого документа как раз использовала
  generated-колонку (`GENERATED ALWAYS AS (opens_at + voting_window_seconds
  * INTERVAL '1 second') STORED`) — идея была правильная (в
  `03-deduplication.md` зафиксировано «TTL = `closes_at` опроса», и явный
  расчёт в коде приложения — источник ровно того класса багов, который там
  разбирался на примере фиксированного TTL), но сам DDL не проходит:
  прогнал его на реальном Postgres 16 в docker, и `CREATE TABLE` падает с
  `ERROR: generation expression is not immutable`. Причина — оператор
  `timestamptz + interval` в Postgres помечен `STABLE`, а не `IMMUTABLE`
  (арифметика с датами формально зависит от часового пояса сессии из-за
  перехода на летнее/зимнее время), а generated-колонки требуют
  immutable-выражение. Ограничение действует на любое выражение вида
  `timestamptz + interval`, независимо от того, что именно в интервале —
  даже если там только секунды.

  Триггер даёт ту же гарантию не поломанным способом: приложение может
  вообще не трогать `closes_at`, значение всегда проставляется `BEFORE
  INSERT OR UPDATE` из `scheduled_at`/`voting_window_seconds` — так же
  невозможно рассинхронизировать вручную. Проверено на реальном Postgres 16
  (`backend/migrations/0001_init.sql`, применена в CI/локально через
  `goose`): вставка опроса без `scheduled_at` (draft) даёт
  `closes_at = NULL`, установка `scheduled_at` при `voting_window_seconds
  = 300` даёт `closes_at` ровно на 5 минут позже.
- `state` — `TEXT + CHECK`, не Postgres `ENUM`: добавление нового состояния
  в `ENUM` требует `ALTER TYPE`, что подключает лишнюю сложность миграций
  ради множества из 4 значений, которое почти наверняка не изменится.
- `scheduled_at`/`closes_at`/`opened_at`/`closed_at` — четыре разных
  момента: `scheduled_at` — плановое время эфира, единственный вход для
  `closes_at` (см. врезку выше); `closes_at` — расчётное время закрытия,
  фиксируется в момент планирования и не сдвигается фактическим открытием;
  `opened_at` — когда опрос реально перешёл в `open` (может отличаться от
  `scheduled_at` на секунды из-за прескейлинга или ручного вмешательства);
  `closed_at` — когда реально закрылось (может быть раньше `closes_at`,
  если админ закрыл вручную досрочно). Разница между `closes_at` и
  `closed_at` — единственный способ отличить в данных «закрылось по
  расписанию» от «закрыли руками раньше срока».
- Нет `created_by`/`actor`: в системе один статический admin-токен без
  ролей (`01-stack.md`, «Аутентификация админки») — писать в схему поле,
  которое всегда будет одним и тем же значением, бессмысленно.

### 1.2 `poll_options`

```sql
CREATE TABLE poll_options (
    poll_id     UUID NOT NULL REFERENCES polls(id) ON DELETE CASCADE,
    ordinal     SMALLINT NOT NULL CHECK (ordinal >= 1),
    label       TEXT NOT NULL CHECK (length(label) BETWEEN 1 AND 200),
    PRIMARY KEY (poll_id, ordinal)
);
```

`ordinal` (1, 2, 3…) — это и есть `option_id` из `api/openapi.yaml`, а не
отдельный суррогатный UUID. Причина: `option_id` — операнд поля хеша в
Redis (`HINCRBY poll:{id}:counts:{shard} {option_id} 1`) на горячем пути,
и лишние байты там платятся на каждый голос, а не один раз. У опций нет
собственной жизни вне опроса (на них никто не ссылается извне), так что
глобальная уникальность UUID здесь не нужна — только уникальность внутри
опроса, которую и даёт составной PK.

Инвариант «`ordinal` идут подряд 1..N без дыр» не оформлен как DB-констрейнт
(это потребовало бы триггера ради множества из ≤50 строк) — он гарантирован
тем, что опции вставляются один раз, одной транзакцией, при создании опроса,
и `05-api-contract.md` уже исключил `PATCH`/`DELETE` для опроса. Раз опции
неизменяемы после создания, а создаются только одним кодовым путём — дыры
взяться неоткуда.

### 1.3 `poll_result_snapshots`

```sql
CREATE TABLE poll_result_snapshots (
    poll_id                 UUID NOT NULL REFERENCES polls(id) ON DELETE CASCADE,
    snapshot_at             TIMESTAMPTZ NOT NULL,
    total_accepted          BIGINT NOT NULL,
    rejected_duplicate      BIGINT NOT NULL DEFAULT 0,
    rejected_rate_limited   BIGINT NOT NULL DEFAULT 0,
    option_counts           JSONB NOT NULL,       -- {"1": 12345, "2": 6789}
    sampling_enabled        BOOLEAN NOT NULL DEFAULT false,
    sampling_rate           INTEGER,              -- K в "1 из K", NULL если выключено
    PRIMARY KEY (poll_id, snapshot_at)
);
```

Пишет воркер раз в секунду, пока опрос открыт (`01-stack.md`,
`02-load-model.md` §6.6). Значения — не дельты, а текущее состояние
Redis-счётчиков на момент снятия: `total_accepted` и `option_counts` растут
монотонно от снапшота к снапшоту, ровно как растут сами Redis-счётчики.

**Почему `option_counts` — `JSONB`, а не отдельная таблица
`(poll_id, snapshot_at, option_ordinal, count)`.** Нормализованный вариант
дал бы до 50 строк на каждый снапшот × ~300–600 снапшотов на опрос — не
проблема для Postgres по объёму (см. §3), но это усложнило бы и запись
(вставка пачкой вместо одной строки раз в секунду), и чтение для
`/results/timeseries` (нужна агрегация обратно в массив вместо одной строки
на точку). Одна JSONB-колонка ровно повторяет форму `ResultsSnapshotPoint`
из `api/openapi.yaml` — воркер пишет одну строку в секунду, а не пачку.
`label` в снапшоте не хранится — он не меняется (опрос неизменяем после
публикации) и подтягивается из `poll_options` при чтении.

`sampling_enabled`/`sampling_rate` — на уровне снапшота, а не опроса,
потому что деградация уровня 2 (`02-load-model.md` §6.7) — это состояние,
которое может включиться и выключиться посреди эфира; фиксировать его как
свойство опроса целиком стёрло бы, когда именно это произошло. Активация
самого режима — механизм оперативного реагирования на инцидент, а не часть
обычного админского флоу, и в `api/openapi.yaml` намеренно не заведён под
неё эндпоинт — это открытый пункт, см. §6.

Составной PK `(poll_id, snapshot_at)` покрывает оба паттерна чтения без
дополнительного индекса: «последний снапшот» (`ORDER BY snapshot_at DESC
LIMIT 1`) для `/results` и «вся история» (`ORDER BY snapshot_at ASC`) для
`/results/timeseries`.

### 1.4 `admin_audit_log`

```sql
CREATE TABLE admin_audit_log (
    id            BIGSERIAL PRIMARY KEY,
    occurred_at   TIMESTAMPTZ NOT NULL DEFAULT now(),
    action        TEXT NOT NULL,          -- 'poll.create' | 'poll.transition' | 'warmup.trigger'
    poll_id       UUID REFERENCES polls(id),
    detail        JSONB NOT NULL DEFAULT '{}'::jsonb
);

CREATE INDEX admin_audit_log_poll_id_idx ON admin_audit_log (poll_id);
```

`poll_id` нужен nullable — не каждое админское действие привязано к опросу
(`/internal/warmup` без `poll_id` в теле). Ценность этой таблицы — именно
**история** переходов: `polls` хранит только текущее и последнее значения
таймстемпов, а `detail` при `action='poll.transition'` хранит запрошенный
переход (`{"from": "scheduled", "to": "open"}`) — то, что из самой таблицы
`polls` после следующего перехода восстановить уже нельзя.

## 2. Redis

> **Обновлено при реализации** — весь этот раздел, не отдельными правками.
> Изначальная схема опиралась на Lua-скрипт с 4 ключами
> (`poll:{id}:meta`, dedup, `counts:{shard}`, `rejected:{shard}`). Она
> физически не работает в Redis Cluster: эти 4 ключа рандомизированы
> независимо (шард — случаен, `nonce` — случаен), значит почти всегда
> попадают в разные слоты кластера, а `EVAL`/`EVALSHA` требует, чтобы все
> ключи скрипта были в одном слоте — `CROSSSLOT Keys in request don't hash
> to the same slot`, воспроизведено на реальном Redis 7 в cluster-режиме
> до того, как это ушло в код. Ниже — что заменило старую схему, и
> почему это не просто «обошли баг», а и проще: `poll:meta` и
> шардирование `counts`/`rejected` были нужны только потому, что счётчик
> инкрементился в Redis на каждый голос; раз это больше не так
> (`01-stack.md`), в них нет необходимости независимо от CROSSSLOT.

| Ключ | Тип | Пишет | Назначение |
|---|---|---|---|
| `d:{poll_id}:{nonce}` | STRING, `SET NX GET EX` | обработчик голосования | dedup-ключ — единственная запись в Redis на голос, `03-deduplication.md` |
| `poll:{id}:counts` | HASH, поле = `option_id` | флашер, раз в секунду | агрегированные голоса, источник `PollResults.options[].count` |
| `poll:{id}:rejected` | HASH, поля `duplicate`/`rate_limited` | флашер, раз в секунду | источник `PollResults.rejected` |
| `leader` | STRING, `SET NX EX` + продление | снапшоттер / автоматические переходы по расписанию | лиз лидерства, один на процесс-флот (`internal/leader`), не один на задачу |

Определение опроса (`state`/`closes_at`/`option_count`) в Redis не
зеркалируется вообще: обработчик голосования читает его из in-process
кеша Go (`internal/cache`, обновляется из Postgres раз в секунду плюс
синхронно при каждом переходе — см. §3), а не из Redis. Это тоже следствие
отказа от Lua: Lua-скрипту нужен был Redis-доступный источник этих полей,
потому что Lua не может обратиться ни к Postgres, ни к памяти Go-процесса;
обычному Go-коду для той же проверки не нужен ни один поход в сеть вообще.

### 2.1 Дедупликация и приём голоса — без Lua

Проверка и приём — одна команда Redis (не Lua-скрипт):

```
SET d:{poll_id}:{nonce} {option_id} NX GET EX ttl
```

Атомарность даёт сама команда `SET NX` — независимо проверено 500
параллельными вызовами на реальном Redis 7 (ровно один `OK`) и
интеграционным тестом на 200 горутин с одним `nonce`
(`internal/store/redisstore`, ровно один `accepted`). Флаг `GET` заодно
возвращает значение, записанное первым (успешным) вызовом, если ключ уже
занят — клиент, потерявший ответ и повторивший запрос тем же токеном,
узнаёт, каким вариантом уже проголосовал, а не только факт отказа.

Всё остальное (проверка `state`/`closes_at`/диапазона `option_id`)
происходит в Go до этой команды, читая закешированное определение опроса
— см. §2 выше. Если что-то из этого не проходит, до Redis дело вообще не
доходит: `closed` и `invalid_option` не порождают никакой записи и
никакого round-trip'а к Redis.

### 2.2 Счётчики — не пишутся на голос

Принятый голос инкрементит `atomic.Int64` в памяти Go-процесса
(`internal/counter`), не Redis. Раз в секунду фоновый флашер сливает
накопленные с прошлого тика дельты одним пайплайном:

```
HINCRBY poll:{id}:counts {option_id} {delta}
HINCRBY poll:{id}:rejected duplicate {delta}
HINCRBY poll:{id}:rejected rate_limited {delta}
```

(только для полей с ненулевой дельтой). Если пайплайн падает, дельты
возвращаются обратно в in-memory счётчик, а не теряются — Redis-сбой
задерживает попадание голосов в Redis, а не теряет их; финальный флаш
происходит и при штатном шатдауне процесса (`SIGTERM`), проверено
end-to-end: голос, поданный за доли секунды до `docker compose stop`,
всё равно оказывается в Redis.

Поскольку запись в `poll:{id}:counts` идёт не чаще раза в секунду (а не на
каждый голос), проблема hot key, из-за которой изначально шардировался
этот ключ (`02-load-model.md` §4.3), не возникает: даже при 75k
голосов/сек в Redis прилетает 1 `HINCRBY`-пайплайн в секунду на этот ключ,
а не 75 000. `closed` (голосование вне окна) в Redis по-прежнему не
пишется — как и в исходной версии, у него нет продуктовой ценности как
сигнал накрутки в отличие от `duplicate`, только видимость через
Prometheus (`votes_rejected_total{reason="closed"}`).

### 2.3 Лидерство — один лиз на несколько задач

`leader` — не специфичен для снапшоттера. Авто-открытие опросов по
расписанию (B4, см. `docs/ai/sessions/02-backend.md`) — тоже периодическая
задача, которая должна выполняться только на одном инстансе; вместо
отдельного лиза под каждую задачу обе используют один и тот же
(`internal/leader.Elector`) — один координатор на процесс-флот, а не два
независимых, чтобы разные инстансы не оказывались лидерами по разным
задачам одновременно без причины. Механизм — `SET NX EX` для захвата,
`GET` + `EXPIRE` для продления, без Lua: узкое окно гонки между проверкой
владения и продлением принято сознательно (`internal/leader`'s doc
comment) — снапшот идемпотентен по построению (§1.3, монотонность), а
переход состояния опроса и так защищён `SELECT ... FOR UPDATE`
(`PollStore.TransitionPoll`), так что даже кратковременное двойное
лидерство не портит данные.

## 3. Переход состояний: Postgres ↔ in-process кеш на каждом инстансе

> **Обновлено при реализации.** Раздел ниже описывал порядок записи
> Postgres → Redis (`poll:meta`). Такого зеркала в Redis больше нет
> (§2) — вопрос теперь не «в каком порядке писать Postgres и Redis», а
> «как определение опроса из Postgres попадает в in-process кеш каждого
> Go-инстанса», и это Redis вообще не касается.

Postgres остаётся единственным источником истины, и переход состояния —
одна транзакция с `SELECT ... FOR UPDATE` (`PollStore.TransitionPoll`), так
что сам переход не может рассинхронизироваться сам с собой даже при гонке
двух одновременных запросов (проверено: 20 конкурентных
`scheduled → open` на один опрос дают ровно один `200`, девятнадцать
`409`). Открытый вопрос — не корректность записи, а то, когда каждый
Go-инстанс **узнаёт** об уже случившемся переходе, потому что хендлер
голосования читает не Postgres, а локальный кеш процесса (§2).

Два механизма, а не один:

- **Фоновый, для всех инстансов**: кеш каждого процесса обновляется раз в
  секунду из Postgres (`internal/cache.Cache.Run`) — до 1с задержки,
  тот же бюджет, что и у снапшотов (§1.3).
- **Синхронный, для инстанса, обработавшего запрос**: сразу после
  успешного `TransitionPoll`/`CreatePoll` админский хендлер вызывает
  `PollCache.Put(poll)` — обновление видно немедленно, без ожидания
  фонового тика.

**Синхронный путь появился не по плану, а по находке при тестировании.**
До него голос, поданный сразу после `scheduled → open` (в пределах той же
секунды), видел устаревшее закешированное состояние `scheduled` и получал
`409 closed` — ложный отказ реального голоса, притом что опрос уже был
открыт в Postgres. Это неверная сторона ошибки по R14 (ложноположительная
блокировка дороже пропущенной накрутки), и именно поэтому `Put` сделан
синхронным, а не оставлен на усмотрение фонового тика: воспроизведено и
закрыто end-to-end (голос сразу после `open`, без задержки, стал приниматься
корректно), лог — в `docs/ai/sessions/02-backend.md`.

**Остаточное ограничение, названное явно, а не скрытое.** `Put` обновляет
кеш только того инстанса, который обработал admin-запрос. Если голос
приходит на **другой** инстанс сразу после перехода, для него всё ещё
действует фоновый тик — окно до 1с. Для одного инстанса локально (как в
этом репозитории, `docker-compose` с одной репликой `api`) это окно
отсутствует полностью; для кластера с несколькими репликами оно сокращается
с «до тех пор, пока чей-то тик не подхватит» до «до 1с на всех инстансах,
кроме того, что исполнил переход» — тот же принцип «занижение хуже
задержки» (R14), применённый последовательно, не решённый до нуля
специально: 1с — тот же бюджет эвентуальной согласованности, что уже принят
для снапшотов и результатов (§1.3, `02-load-model.md` §6.6).

`/internal/warmup` (`05-api-contract.md`) при указанном `poll_id`
принудительно делает то же самое (`PollCache.Get` с fetch-through) —
операторский рычаг прогреть конкретный опрос в кеше перед эфиром, не
дожидаясь ни фонового тика, ни первого реального запроса.

## 4. Масштаб — почему тюнинг Postgres не нужен

Проверка утверждения из `01-stack.md`/`02-load-model.md` §4.6 на
конкретных числах:

| Таблица | Строк на один опрос | Частота записи |
|---|---|---|
| `polls` | 1 | раз на опрос |
| `poll_options` | ≤50 | раз на опрос, одной транзакцией |
| `poll_result_snapshots` | ~300–600 (окно 5 мин, снапшот раз в секунду) | 1 INSERT/сек, только пока опрос открыт |
| `admin_audit_log` | единицы | на каждое админское действие |

Даже при 1000 опросов за время жизни продукта — это ~600К строк в
`poll_result_snapshots`, тривиально для Postgres без партиционирования и
дополнительных индексов. Утверждение «Postgres не узкое место» из
`02-load-model.md` §4.6 подтверждено на уровне конкретной схемы, а не
только качественно.

## 5. Что сознательно не делаем

| Что | Почему нет |
|---|---|
| Партиционирование `poll_result_snapshots` по времени | §4 — счёт на сотни тысяч строк, не миллиарды. |
| `ENUM` для `state` | Одна ALTER TYPE ради 4 значений, которые вряд ли изменятся — не окупается. |
| Отдельная таблица под опции вместо JSONB в снапшотах | Обсуждено в §1.3 — усложняет и запись, и чтение таймсерии ради нормализации, которая здесь не нужна (снапшот и так один агрегат на момент времени). |
| `actor`/`created_by` в audit log | Один статический admin-токен, различать некого (`01-stack.md`). |
| DB-констрейнт на непрерывность `ordinal` в `poll_options` | Гарантировано конструкцией (один код-путь создания, без edit), см. §1.2. |

> существу.

- **Механизм включения sampling (деградация уровня 2).** Схема данных под
  него готова (`sampling_enabled`/`sampling_rate` в снапшотах), но кто и

  сам API (шаги 1–9) реализован полностью.
